# Phase 4D — X (Twitter) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add X to the posting pipeline: connect an X account, upload the video in pieces relayed through Clipy's server, and create the post once X has processed the video.

**Architecture:** X requires the user's token on every upload request and documents a chunked protocol (initialize → append segments → finalize → status), so X uses the `relay` protocol built in 4A: the phone sends ≤ 4 MiB pieces to `post-upload`, which appends each as one segment; the token never reaches the phone. Because the post is created by the server after processing — a step that must never run twice — the status path of the session state machine first becomes claim-guarded (Task 1), which also tightens Instagram and Facebook.

**Tech Stack:** as 4A–4C.

**Spec:** `docs/superpowers/specs/2026-10-02-phase-4-direct-posting-design.md` (§10 overrides). Research with source URLs: `docs/superpowers/research/p4-research-x.md`.

### Task 1: Serialise the status path (claim-guarded polling)

**Files:**
- Modify: `supabase/functions/_shared/handlers/{session,postStatus,postFinalize}.ts`, `supabase/functions/_shared/__tests__/post.test.ts`, `supabase/functions/_shared/types.ts` (comment on `publishing` only if needed)

**Behaviour** (replaces the current "processing → adapter.status with no claim" rule; everything else in the state machine stays):
- For a session in `processing`, the status logic first does `claimSession(id, "processing", "publishing")`.
  - Lost the claim → re-read the session and answer from its new state: `done` → settled; `failed` → throw the stored error; `publishing` or `processing` → `{ status: "processing" }` (no adapter call); `uploading` → 400 "Finish the upload first.".
  - Won → call `adapter.status(...)` (through `withPlatformAuth`):
    - done → `claimSession(id, "publishing", "done", { url })`; return it.
    - processing → `claimSession(id, "publishing", "processing")`; return it.
    - a final rejection (`isRejection`) → `claimSession(id, "publishing", "failed", { error })`; rethrow.
    - anything else (reconnect, temporary, non-ApiError) → `claimSession(id, "publishing", "processing")`; rethrow. (The session goes back to `processing`, not `uploading`: the publish step has already been started once.)
  - As in finalize, only the adapter call is wrapped by the try/catch that decides the outcome; if a claim write itself throws after the adapter returned, let it propagate (the session stays `publishing` — the accepted dead-end).
- `postFinalize` delegating a `processing` session uses this same logic.
- Result: at most one `adapter.status` call per session is in flight at any time.

- [ ] **Step 1: Failing tests** (add to `post.test.ts`; keep every existing test green or update it only where it asserted the old unguarded behaviour — list each change in the report):
  - two `postStatus` calls with `Promise.all` on a `processing` session whose fake `adapter.status` resolves after an awaited tick → `adapter.status` called exactly once; both results are valid; the session ends in the state the adapter's answer implies.
  - status while another status is in flight (session set to `publishing` directly) → `{ status: "processing" }`, adapter not called, session unchanged.
  - adapter.status → done: session `done` with the url; → processing: session back to `processing`; → PlatformError 400: session `failed` with the message, error rethrown; → PlatformError 503: session `processing`, rethrown; → a `TypeError`: session `processing`, rethrown; → auth error: session `processing`, account flagged, `reconnect` thrown.
  - a claim write throwing after `adapter.status` resolved done → the call rejects and the session is not reverted to `processing` (stays `publishing`).
  - finalize on a `processing` session goes through the same guarded logic (adapter.status called once when raced with a status call).

### Task 2: X server adapter, setup guide

**Files:**
- Create: `supabase/functions/_shared/platforms/x.ts`, `supabase/functions/_shared/__tests__/x.test.ts`
- Modify: `platforms/registry.ts`, `supabase/README.md`

**Behaviour** (`id: "x"`, `secrets: ["X_CLIENT_ID", "X_CLIENT_SECRET"]`, API base `https://api.x.com`, scopes `tweet.read tweet.write users.read media.write offline.access`):
- `authUrl`: `https://x.com/i/oauth2/authorize?response_type=code&client_id&redirect_uri&scope&state&code_challenge=<given>&code_challenge_method=S256`.
- `exchange({ code, codeVerifier })`: `POST /2/oauth2/token`, form body `code`, `grant_type=authorization_code`, `redirect_uri`, `code_verifier`; header `Authorization: Basic base64(client_id:client_secret)`. Maps `access_token`, `refresh_token`, `expires_in`, `scope`. A response without `access_token` is an error.
- `refresh`: same endpoint, `grant_type=refresh_token`, `refresh_token`; Basic auth; returns the NEW refresh token (rotation).
- `revoke`: best effort `POST /2/oauth2/revoke` form `token=<refresh or access>`, `token_type_hint`, Basic auth; failures ignored.
- `profile`: `GET /2/users/me?user.fields=profile_image_url` → `{ accountId: id, displayName: "@" + username, avatarUrl: profile_image_url ?? null }`.
- `prepare`: `POST /2/media/upload/initialize` JSON `{ media_type: <input mime>, total_bytes: <fileSize>, media_category: "tweet_video" }` → `data.id`; returns `{ protocol: "relay", uploadUrl: null, uploadHeaders: {}, chunkSize: 4 * 1024 * 1024, ref: { mediaId }, wait: { maxSeconds: 300, intervalSeconds: 5, resumeOnTimeout: true } }`.
- `relayChunk(ref, { offset, total, body })`: `offset % chunkSize` must be 0 (else `PlatformError("x", 400, "Unexpected upload position.")`); `POST /2/media/upload/{mediaId}/append` as `multipart/form-data` with fields `segment_index = offset / chunkSize` and `media` = the bytes (build the multipart body by hand as a `Uint8Array` with an explicit boundary, or with `FormData` + `Blob` — choose whichever works identically in Node 22 and Deno, and test the produced body); returns `{ nextOffset: offset + body.length }`.
- `finalize`: `POST /2/media/upload/{mediaId}/finalize`; then `publishWhenReady` with the returned `processing_info`.
- `status`: `GET /2/media/upload?command=STATUS&media_id={mediaId}` → `publishWhenReady`.
- `publishWhenReady(processing_info)`: no `processing_info` or `state: "succeeded"` → create the post; `pending` / `in_progress` → `{ status: "processing" }`; `failed` → `PlatformError("x", 400, "X couldn't process this video." + (error message ? " " + message : ""))`.
- Create the post: `POST /2/tweets` JSON `{ text: <caption cut to 280 weighted characters>, media: { media_ids: [mediaId] } }` → `data.id` → `{ status: "done", url: "https://x.com/i/status/<id>" }`. A 403 whose `detail`/`title` says the content is a duplicate → `{ status: "done", url: null }` (an earlier attempt already posted it). Any other failure keeps its classification (4xx final, 429/5xx temporary, 401 reconnect).
- Errors: X's problem JSON `{ title, detail, type, status }` (and `errors[0].message` for the older shape) → `PlatformError("x", <http status>, detail || title || message)`, `reason` = the last path segment of `type` when present.
- `isAuthError`: reason `unsupported-authentication` or `client-not-enrolled`? — NO: those are configuration/billing problems, not a broken grant; surface them verbatim. Only HTTP 401 reconnects (default rule). Leave `isAuthError` undefined.
- `weightedLength(text)` and `cutToWeighted(text, 280)` exported from `x.ts`: code points in U+0000–U+10FF, U+2000–U+200D, U+2010–U+201F, U+2032–U+2037 weigh 1, everything else 2; each `https?://\S+` counts 23.
